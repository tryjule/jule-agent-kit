# Jule in this workspace

In this workspace, pop-ups, sign-up and newsletter forms, quizzes and surveys, preference centers, unsubscribe pages and landing pages are built as Jule projects through the `jule` MCP server — from Jule items (`text`, `logo`, `icon`, `button`, `input`, `flex` Boxes), never as HTML, CSS, React or any other files unless the user explicitly asks for a standalone website or code, and never as `html-block` items standing in for headings, copy, images, fields, buttons, sections or pages (an `html-block` is for one embed, table or piece of vector art the items cannot show) — and what runs them (coupons and coupon codes, show-rule triggers, A/B tests, webhook subscriptions, branding, analytics) is done through the same server. This holds in any wording, whether or not the user says "Jule", and including "build this from the Figma design"; a pop-up, form, quiz, landing page or coupon means Jule, not another connector. When it is unclear whether they want a Jule project or code, ask before starting.

Jule is the product the user bought: a hosted builder for pop-ups, forms, quizzes, preference centers and landing pages, published from the Jule dashboard. The `jule` MCP server (`https://api.jule.ai/mcp`, sign in with the user's Jule account) is how an assistant authors, previews, operates and analyzes those projects. The skills in this repository say how:

- `skills/jule-builder/SKILL.md` — build or change a pop-up, form, quiz, preference center or landing page from a brief.
- `skills/figma-to-jule/SKILL.md` — build one from a Figma design read through the Figma MCP server.
- `skills/jule-analytics/SKILL.md` — read a project's numbers and turn them into one grounded recommendation.

Rules that hold for every Jule task:

1. Call `whoami` first, once. When the organization has more than one workspace and the user did not name one, list them by name and ask which to use before reading or writing anything; never choose for them (one workspace: use it and say so). Ask with names, not ids.
2. Before authoring or changing a project read the guides `jule://docs/item-catalog`, `jule://docs/project-style` and `jule://docs/settings` (`jule://docs/responsive` for device widths, `jule://docs/languages` for translations), copy the shape of the matching `jule://docs/examples/{popup|preference-center|landing-page}` document instead of composing one from scratch, then read `jule://workspaces/{id}/branding`, `jule://workspaces/{id}/integrations` and `jule://workspaces/{id}/events` for the target workspace. Hosts that do not read MCP resources find the same guides under each skill's `references/`, or ask the server for one through `whoami` with `doc` set to the guide name and `section` to one item type or heading (bounded, with the list of sections). The document schema is served in parts — `jule://docs/schema/items/{type}`, `jule://docs/schema/style_config`, `jule://docs/schema/settings_config`, `jule://docs/schema/document`; `references/document-schema.json` is the whole file — and is read only for a field the guides leave open: every validation error already carries the field's description and allowed values.
3. Change only what the brief asks for; every other style and settings field gets the editor default. Do not add effects, shadows, overlays, animations or colors the user did not mention. A pop-up has no backdrop unless the brief asks for a dimmed page. Build from items: validation and every save warn when an `html-block` holds page content or form controls; rebuild what you wrote as items, say which parts fell back to `html-block` and why, and leave blocks the user built in the editor as they are.
4. Before `create_project`, call `list_projects` with `search` set to the intended name; if a project with that name exists, ask whether to update it or create another.
5. Validate with `validate_project_document` until it passes and fix its warnings (the dashboard's publish checks, responsive and translation completeness), then save. After every create, save, patch or duplicate show the preview without being asked: put `preview_url` on its own line exactly as returned and say it expires in ten minutes; `preview_project` with `device: "all"` gives the desktop, tablet and mobile links — open the mobile one before calling a project done.
6. Never publish on your own. Tools that affect live traffic (`set_project_status`, `experiment_action` with conclude or promote_winner, `manage_branding_asset` deletes) answer with a summary and `requires_confirmation`; show the summary and call again with the `confirmation_token` only after the user explicitly agrees.
7. Not available through the tools — say so and point to the dashboard: inviting or managing users and roles, API keys and secrets, setting or verifying a custom domain (its status and the install snippet are readable in `jule://projects/{id}/embed`), the workspace one-click-unsubscribe setting, creating or editing webhook destinations, billing.
8. Speak about Jule as the product. When data is missing or a call fails, say so in one sentence, offer the dashboard or Jule support (support@jule.ai), and move on; never guess at how Jule is built or hosted.
9. When the user needs something the tools cannot deliver, say plainly what is not possible; if it was a real need that stayed blocked or degraded, record it once with `report_capability_gap`, relay its `user_message` verbatim (the request went to the Jule team, who are working on it), then say what you did instead. Describe the capability, never the person.
